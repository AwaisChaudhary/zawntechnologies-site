MVP development: what to build first and what to leave out

By Awais Chaudhry, 22 November 2026

Quick answer: an MVP should contain only the one core action that proves people want your product, plus the minimum around it to make that action work: sign-in, the core workflow, a way to pay or commit if money is part of the test, basic notifications, a simple admin screen and analytics. Leave out multiple user roles, advanced settings, social features, a second platform, automation of rare tasks and polished extras. A focused MVP is usually 250 to 450 hours of work, about $12,500 to $22,500 at $50 per hour, and 6 to 12 weeks from agreed scope to launch.

Most MVPs that run over budget do not fail because the code was hard. They fail because the first version tried to be the finished product. This guide gives you a practical way to decide what goes into version one, what waits, and how to spot the features that quietly double a budget. It is written from the engineering side: we scope, design and build first versions for founders, and the same questions come up on almost every project.

What is an MVP, really?

A minimum viable product is the smallest version of your product that real users can use for its main purpose, so you can learn whether it solves their problem and whether they will pay or keep coming back. The key word is viable: it must work properly for one job. A half-built version of ten features teaches you nothing, because users cannot tell you whether the idea is wrong or the product is just unfinished.

An MVP is also not the same as a prototype. A clickable prototype in Figma tests whether people understand the idea and the flow. An MVP is real software with real data, so it tests behaviour: do people sign up, complete the core action, pay, and return?

How do you decide what to build first?

Start from the riskiest assumption, not the feature list. Write one sentence: "We believe [type of user] will [do the core action] because [reason]." Everything in the MVP should exist to test that sentence.

1. Name the core action

Every product has one action that delivers the value. For a marketplace it is a buyer booking or buying from a seller. For a booking tool it is a customer making a booking. For an AI product it is the user getting a useful result from their own input. For a sports analysis app it is a player uploading a video and seeing a measurement they trust. If a feature does not help a user reach that action, or help you learn from it, it is a candidate for later.

2. Map the shortest path to that action

List each step a new user takes from first visit to completing the core action once. Each step usually becomes one or two screens. A focused MVP has roughly 5 to 8 core screens. If your path needs 20, either the product is doing too many jobs or some steps can be done by hand for now.

3. Sort every other feature with MoSCoW

Put each remaining idea into one of four groups:

  • Must have: the product does not work, or is not legal or safe to run, without it.
  • Should have: important, but users can complete the core action without it. Usually phase two.
  • Could have: nice to have. Wait until users ask for it.
  • Won't have (this version): written down so it is a decision, not a forgotten idea.

Be strict with "must have". A useful test: would you delay launch by a month for this feature? If not, it is not a must.

4. Replace features with manual work where you can

Many features can be done by a person behind the scenes for the first few hundred users. Approving sellers, matching customers with providers, sending onboarding emails, issuing refunds, producing a weekly report: all of these can start as a task for you in an admin screen or a spreadsheet. You learn exactly how the process should work before paying to automate it.

What to leave out of an MVP

  • A second platform. Launch on web, iOS or Android first, or use one cross-platform codebase. Building native iOS and Android separately roughly doubles front-end work. Our guide on iOS or Android first covers how to choose.
  • Multiple user roles and permission levels. Team accounts, managers, sub-admins and custom permissions add screens and testing everywhere. Start with one user type per side.
  • Social features. Feeds, comments, likes, follows and in-app chat are expensive and rarely the reason people sign up. A simple email notification often does the job of chat at first.
  • Advanced settings and personalisation. Pick sensible defaults and see what people actually ask to change.
  • Complex search and filters. With a few hundred items, basic search and two or three filters are enough.
  • Automating rare tasks. Anything that happens weekly or less can be manual for now.
  • Many integrations. Each third-party system (CRM, accounting, calendar, ERP) adds setup, edge cases and maintenance. Keep only the one the core action needs.
  • Multiple languages and currencies, unless your launch market requires them.
  • Custom animations and illustrations. Clean, consistent design matters; decoration can wait.

Features that quietly double an MVP budget

Some requests sound small in a brief but carry a lot of hidden work. Watch for these:

  • "Real-time" anything: live tracking, live chat, live dashboards. They need different infrastructure and much more testing than screens that refresh.
  • Offline mode: syncing data that changed on a phone and a server at the same time is a hard problem.
  • Two-sided payments and payouts: splitting payments between a platform and sellers involves onboarding, identity checks, refunds and disputes. Start with the simplest flow your payment provider supports.
  • AI features with an accuracy target: a demo is quick; dependable results take testing, data and tuning. Prove the AI part separately before building the full app around it.
  • Importing messy existing data: spreadsheets, old systems and legacy databases nearly always need cleaning.

Should you use no-code for your MVP?

Sometimes, yes. A no-code platform such as Bubble.io can cut the cost of a first web app, especially for marketplaces, directories and internal tools with standard forms and workflows. Custom code makes more sense when the core action depends on heavy processing, computer vision, real-time features, native device features or very specific performance needs. We build both and compare them in detail in Bubble.io vs custom code. For custom-coded mobile MVPs, a single cross-platform codebase is usually the best value; see Flutter vs React Native.

A simple MVP plan, step by step

  1. Discovery (about a week): agree the core action, the riskiest assumption, the must-have list and what success looks like, for example a target number of completed bookings or paid sign-ups.
  2. Design: wireframes of the core path, then a clickable prototype you can show to five or more potential users before code is written. See our UI/UX design service.
  3. Build in milestones: working software every one to two weeks, so you can cut or change scope based on what you see.
  4. Test: the core path on real devices and browsers, payments in test mode, and the admin tasks. Our QA and testing team handles this before release.
  5. Launch small: a limited group of users first, watch the analytics, talk to users, then fix and expand.
  6. Decide phase two from data: build the "should have" features users actually ask for, not the ones you guessed.

Common MVP mistakes

  • Building for every type of user at once instead of one clear first audience.
  • Skipping analytics, then having no way to tell why users drop off.
  • Polishing the design for months before a single real user has tried it.
  • Treating the MVP as throwaway code. Shortcuts in scope are fine; shortcuts in code quality and security make phase two slower and more expensive.
  • Not owning the code and accounts. Your repository, app store accounts, domain and cloud hosting should be in your name from day one.

Questions about MVP scope

How many features should an MVP have?

As few as it takes to complete one core action properly. In practice that is sign-in, the core workflow, payments if they are part of the test, basic notifications, a simple admin screen and analytics, usually 5 to 8 core screens. Everything else waits until users ask for it.

How long should it take to build an MVP?

Most focused MVPs take 6 to 12 weeks from agreed scope to launch, depending on platforms and integrations. If the plan is much longer than three months, the scope usually includes features that can wait for phase two.

Is an MVP the same as a prototype?

No. A prototype, often clickable designs, tests whether people understand the idea and the flow. An MVP is working software with real data, so it tests whether people actually sign up, complete the core action, pay and come back.
